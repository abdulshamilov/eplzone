# Своя подача

Гость пишет пожелание в свободной форме — «футбольный кофе», «Барселона», «Дюна».
Сервис придумывает под него напиток: название, описание, состав из реального
каталога кофейни, способ подачи и фотографию.

Пока модель думает и рисует, на экране наливается кофе. Это не заставка ради
красоты: генерация фото занимает 5–20 секунд, и анимация закрывает именно это
ожидание.

---

## Нужен ли бэкенд

Да, и по двум причинам.

**Ключи.** Всё, что попало в браузер, можно прочитать: открыть исходный код
страницы или посмотреть сетевые запросы. Ключ от Anthropic и ключ от генератора
картинок в браузере — это чужой счёт за твой кофе. Ключи лежат только в
переменных окружения на сервере и никогда не уходят на клиент.

**Правила.** Цена считается на сервере, а не берётся из ответа модели. Состав
фильтруется по каталогу: если модель придумала ингредиент, которого в кофейне
нет, он не попадёт в заказ. Модель предлагает — сервер решает.

Бэкенд здесь минимальный: одна функция. Отдельный сервер поднимать не нужно.

---

## Как устроено

```
public/index.html     весь фронт: анимация налива, форма, карточка напитка
api/generate.js       единственная ручка: принимает пожелание, отдаёт напиток
api/_text.js          вызов Claude: название, описание, состав, промт для фото
api/_image.js         вызов генератора картинок (три провайдера на выбор)
api/_catalog.js       каталог кофейни, цены, расчёт стоимости
```

Один запрос гостя — это два вызова наружу: сначала текст, потом картинка по
промту, который написала та же модель. Если картинка не получилась, напиток
всё равно вернётся: текст и цена важнее фото.

Сборки нет. `public/index.html` — обычная страница без зависимостей.

## Запуск

```bash
npm install
cp .env.example .env.local     # вписать свои ключи
npx vercel dev                 # http://localhost:3000
```

Деплой:

```bash
npx vercel --prod
```

Ключи в проде добавляются в Vercel → Project → Settings → Environment
Variables. Файл `.env.local` в гит не попадает — он в `.gitignore`.

## Переменные окружения

| Ключ | Зачем |
|---|---|
| `ANTHROPIC_API_KEY` | обязательный, текст напитка |
| `TEXT_MODEL` | по умолчанию `claude-opus-5`; дешевле — `claude-sonnet-5` или `claude-haiku-4-5` |
| `IMAGE_PROVIDER` | `openai`, `replicate` или `fal` |
| `OPENAI_API_KEY` / `REPLICATE_API_TOKEN` / `FAL_KEY` | ключ того провайдера, который выбран |
| `RATE_LIMIT_PER_HOUR` | сколько генераций с одного адреса в час, по умолчанию 20 |

Провайдер картинок меняется одной переменной — код трогать не нужно.
Каждый адаптер в `api/_image.js` — это один запрос и разбор ответа, десяток
строк. Провайдеры меняют параметры чаще, чем выходят релизы: перед первым
запуском сверь тело запроса с актуальной документацией своего провайдера,
править придётся внутри одной функции.

## Сколько это стоит

На одну генерацию:

- **текст** — около 1500 входных токенов (каталог и правила) и 300 выходных.
  Системный промт закеширован, поэтому со второго запроса вход считается
  примерно в десять раз дешевле. На Haiku это доли копейки, на Opus — единицы
  рублей;
- **картинка** — основная статья расходов. У быстрых моделей вроде flux-schnell
  это копейки за штуку, у gpt-image-1 в среднем качестве — заметно дороже.

Практический вывод для пилота: текст можно позволить себе на старшей модели,
экономить нужно на картинке. Если цена на фото станет проблемой, первый шаг —
кешировать картинки по одинаковым пожеланиям, а не понижать модель текста.

---

## Что стоит сделать до пилота

- **Хранилище.** Сейчас каталог лежит в файле, а счётчик запросов — в памяти
  функции: при перезапуске он обнуляется. Для пилота хватит одной таблицы в
  Postgres под каталог и под историю заказов.
- **Кеш картинок.** Одинаковые пожелания приходят чаще, чем кажется.
- **Модерация пожеланий.** Текст гостя уходит в промт как данные, а не как
  инструкции, но фильтр по содержанию всё равно нужен.
